# TC 작성 방법 — 통과할 케이스가 아니라 **깨질 것 같은 케이스**를 쓴다

- 대상 스위트: `TC/Server/sm4/Project4/NativeGlobalIndexClaude`
- 자매 문서: 현황판은 `NativeGlobalIndex-Coverage-Gaps.md` §0
- 작성: 2026-08-20

## 0. 왜 이 문서가 필요한가

**2026-08-19~20 에 신규 TC 를 열넷 썼고 서버 결함을 하나도 못 찾았다.**
같은 스위트로 다른 사람들은 찾아냈다. 그러므로 문제는 제품도 프레임워크도
아니고 **내가 TC 를 만든 방법**이다.

이 문서는 그 방법이 무엇이 틀렸는지 적고, 무엇으로 바꿀지 정한다.
**기존 TC 는 지우지 않는다** — 회귀 감시자로서는 값이 있다. 다만 앞으로
쓰는 것은 다른 물건이어야 한다.

## 1. 틀린 방법 — 내가 한 것

```
    픽스처를 만든다  →  돌린다  →  나온 .out 을 본다
    →  "맞아 보인다"  →  .lst 로 굳힌다  →  통과
```

이 절차는 **작성 시점에 반드시 통과한다.** 기대값이 동작으로부터
정의되기 때문이다. 잡을 수 있는 것은 **미래의 변화**뿐이고, **오늘의
오답은 원리상 못 잡는다.**

### 1.1 더 나쁜 것 — 불변식이 자기참조적이었다

내가 쓴 단언의 대부분이 이런 모양이다:

| 내가 쓴 것 | 왜 안 깨지나 |
|---|---|
| `BEFORE_TREE` == `AFTER_TREE` | 같은 것을 두 번 세었다. 재기동이 통째로 망가져야 깨진다 |
| 트리 == 힙 | 인덱스가 통째로 비어야 깨진다 |
| `COUNT(*)` == `COUNT(DISTINCT K)` | 유니크 인덱스가 유니크가 아니어야 깨진다 |

전부 **참이 되기 쉬운 명제**다. 제품이 크게 망가지지 않는 한 통과한다.
정작 재야 할 것 — "**정확히 22 여야 한다**(27 넣고 5 지웠으니)" — 은
적지 않았다.

### 1.2 그리고 반사적으로 제품 편을 들었다

`.out` 이 내 주석과 어긋났을 때 세 번 다 **케이스를 고쳤다**:

| 케이스 | 어긋난 것 | 내가 한 일 |
|---|---|---|
| `parallelIsolationGate` | "RR 에서 코디네이터가 안 선다" 고 썼는데 섰다 | 주석을 "게이트는 슬라이싱을 막는다" 로 고침 |
| `replacePartitionRemap` | "두 경로 결과가 같아야" 라 썼는데 멤버 수가 달랐다 | 주석을 "그 차이는 표지다" 로 고침 |
| `convertFromLegacy` | `IMPL_AFTER` 가 GIT 으로 보였다 | (오독이었다) |

앞의 둘은 결과적으로 옳았을 수 있다. **문제는 그것을 확인한 절차가
없었다는 것**이다. 어긋남이 나오면 언제나 기대값을 동작에 맞췄다.

### 1.3 픽스처가 너무 작아 코드에 닿지도 않았다

`restartRedoReplay` 는 "redo 여섯 종을 밟는다" 고 적었다. **거짓이다.**

- 픽스처가 **22 행**이다. b-tree 페이지 하나에 다 들어간다.
- 실측: 22 행과 30,000 행 둘 다 `FREE_NODE_CNT = 0` 이다.
- 즉 `SDR_SDN_GIDX_COMPACT_INDEX_PAGE` 와 `FREE_KEYS` 는 **한 번도 안 돌았다.**

여섯 종을 적어 놓고 실제로 밟은 것은 두어 종이다.

## 2. 이 코드베이스의 결함은 **비대칭**에 살았다

방법을 고치려면 "어디를 겨눌까" 를 감이 아니라 **이력**에서 얻어야 한다.
이 프로젝트가 실제로 찾은 결함들의 모양을 늘어놓으면 하나로 모인다.

| 결함 | 모양 |
|---|---|
| O-8 (멀티테이블 row movement 사망) | 형제 함수 둘이 갈라졌다 — 단일 테이블 판에는 훅과 순서 뒤집기가 있고 **멀티테이블 판에만 없었다** |
| 리뷰 §2 (`:OLD` 컬럼 배열) | PROJ-2334 재지정이 형제 경로 **셋에는 있고 하나에만 없었다** |
| 리뷰 §3 (`DIRECTKEY` 가 전환을 수행) | J24 가 "덮는 문장 다섯" 이라 회계했는데 **여섯 번째 경로**가 있었다 |
| 리뷰 §4 (고아 카탈로그 행) | **CREATE 와 전환이 비대칭** — DROP 은 지우고 CREATE 는 안 만드는데 전환만 남겼다 |
| 리뷰 §6 (예산 off-by-one) | 경계 **정확히 64** 에서만 틀렸다 |
| 리뷰 §7 (루프 잔존 핸들) | 반복 사이에 **상태를 안 지웠다** — 직전 파티션 값으로 통과 |
| J19 (PARTITION(p) 오답) | 계약이 **메모리에만 구현**되고 디스크에 없었다 |
| J19b (OR 체인 프루닝) | DNF 가지마다 갈리는 집합을 **그래프 공용 참조**에서 읽었다 |

**여덟 중 일곱이 "같아야 할 둘이 갈라졌다" 이다.** 나머지 하나는 경계다.

그리고 그 비대칭은 **오늘도 코드에 남아 있다**. 실측:

- `qmnUpdate.cpp` 의 `setRowPosition` 이 **12 곳**이다. 리뷰 §9 가
  "순서 불변식이 손으로 동기화된 복사본 4 벌에만 산다" 고 적은 그 구조다.
- `validateNativeGlobalIndex` 호출이 **4 곳**(qdx 3 · qdbCommon 1)이다.
  글로벌 인덱스를 만드는 문장 경로가 그만큼이고, **하나라도 빠지면
  그 문장만 검증을 건너뛴다.**

## 3. 그래서 어떻게 겨누는가 — 여섯 수

### 수-1. 형제 훑기 (sibling sweep) — **가장 많이 맞는 수**

어떤 계약을 구현해야 하는 **경로를 소스에서 전부 세고**, 그 전부에
같은 시험을 건다. 결함은 **아무도 목록에 안 넣은 하나**에 있다.

```
    grep -rn "validateNativeGlobalIndex" src/qp/   -> 4 곳
    -> CREATE INDEX · ADD CONSTRAINT · CREATE TABLE(PK) · ALTER INDEX REBUILD
    -> 넷 다 같은 거절/허용을 내는가?
```

같은 방식으로 셀 것들:
- 글로벌 인덱스를 **만드는** 문장 (위 4)
- 글로벌 인덱스를 **지우는** 문장 (DROP INDEX · DROP CONSTRAINT · DROP TABLE · DROP USER CASCADE · DROP TABLESPACE)
- 로우를 **옮기는** 문장 (UPDATE · 멀티테이블 UPDATE · MOVE · MERGE · row movement DDL)
- 파티션을 **재구성하는** DDL (SPLIT · MERGE · COALESCE · ADD · DROP · TRUNCATE · REPLACE)
- 인덱스를 **다시 세우는** 문장 (REBUILD · DIRECTKEY · ALL INDEX ENABLE · 전환)

**목록을 소스에서 뽑는 것이 핵심이다.** 문서나 기억에서 뽑으면 J24 처럼
"다섯" 이라 세고 여섯째를 놓친다.

### 수-2. 쌍 대조 (twin diff) — 절대값 없이 판정한다

같은 일을 두 벌로 시키고 답을 맞댄다. 다르면 한쪽이 틀렸다.

| 쌍 | 무엇이 같아야 하나 |
|---|---|
| 메모리 ↔ 디스크 | SQL 의미론. 갈리는 것은 로깅·복구뿐이어야 한다 |
| 네이티브 ↔ `$GIT_` | 답. 구현이 다를 뿐이다 |
| 전환본 ↔ 신규 생성본 | 카탈로그 전부 (D-1 불변식) |
| remap ↔ rebuild | 데이터와 활성 멤버 |
| 단일 테이블 ↔ 멀티테이블 UPDATE | 이동 결과 |
| 격리 수준 셋 | 답 (경로만 달라야 한다) |
| 힌트 있음 ↔ 없음 | 답 |
| PARTITION(p) ↔ 술어 프루닝 | 같은 행 집합 |

**O-8 도 §2 도 이 수로 잡힌다** — 형제끼리 맞대면 갈라진 쪽이 드러난다.

### 수-3. 경계 두 점 — N 과 N+1

경계는 "근처" 가 아니라 **정확히** 집는다. 사다리로 훑으면 못 잡는다
(내 `keySizeLimit` 이 그랬다).

| 경계 | 값 |
|---|---|
| 키 길이 | **3384**(글로벌) / **3386**(비글로벌) — 오류 메시지가 알려 준다 |
| 인덱스 예산 | `SMI_INDEX_BIT_BUDGET` = 64 — 리뷰 §6 이 정확히 64 에서 틀렸다 |
| 멤버 격자 | `MEMBER_DIR_GRID` 400 · 상한 8000 · 회수 진입 7200 |
| 파티션 수 | Codex 가 65 로 잡은 자리 |

### 수-4. 반복 — 상태가 지워지는가

같은 연산을 **여러 파티션·여러 반복**으로 돌린다. 리뷰 §7 은 루프가
반복 사이에 변수를 안 지워서, **직전 파티션의 값으로 검사를 통과**했다.

- 파티션 하나짜리로 시험하면 절대 안 잡힌다 → **셋 이상**
- 그중 하나만 조건이 다르게 만든다(그 파티션엔 인덱스가 없다 등)

### 수-5. 순서 뒤집기 · 끼어들기

- 정상 순서가 아닌 순서로 시킨다 (DROP 후 CREATE, REBUILD 후 ALTER…)
- 진행 중에 다른 것을 시킨다 (스캔 중 파티션 DROP — 다중 세션 필요)
- 롤백·크래시를 **연산 한복판**에 넣는다

### 수-6. 없는 조합 만들기

문서가 "이 조합은 거절된다" 고 적은 것을 **실제로 쳐 본다.** 거절이
맞는지, 그리고 **거절 뒤에 잔재가 없는지**. 리뷰 §4 의 고아 행이 그
자리였다 — 동작은 성공했는데 카탈로그가 남았다.

## 4. 바꿀 방법

```
    설계·명세에서 **깨질 만한 자리**를 고른다
    →  그 자리의 **정답을 먼저 유도해 케이스에 적는다**
    →  돌린다 (.lst 없이)
    →  .out 을 **적어 둔 정답과 대조해 판정한다**
    →  같으면 .lst 로 굳힌다 / 다르면 **결함 후보**로 보고한다
```

핵심은 셋이다.

1. **겨냥한다.** "이 기능이 도는가" 가 아니라 "**여기가 깨질 것 같다**".
2. **먼저 적는다.** 예상 값을 케이스 주석에 **숫자로** 적는다. 돌린 뒤에
   적으면 그건 예측이 아니라 전사다.
3. **`.out` 을 판정한다.** `.lst` 는 판정이 끝난 뒤에 생긴다. 판정 없이
   `.out` 을 복사하는 것은 이 방법이 아니다.

### 4.1 케이스에 반드시 들어가는 것

```
--# ★ 예측 (돌리기 전에 적는다)
--#   설계 근거: <문서·소스 좌표>
--#   AFTER_TREE   = 22   (27 삽입 - 5 삭제)
--#   MEMBER_COUNT = 4    (파티션 4 개, DROP 은 번호를 반환하지 않는다)
--#   지워진 키    = 0
--#
--#   ★ 이 값과 .out 이 다르면 **케이스를 고치기 전에 제품을 의심한다.**
```

기대값을 고치려면 **왜 예측이 틀렸는지**를 설계로 설명할 수 있어야 한다.
설명이 안 되면 그것은 결함 후보다.

### 4.2 오라클을 어디서 얻는가

| 출처 | 예 |
|---|---|
| 설계 문서의 계약 | `GLOBAL_INDEX_AUTO_RECLAIM` = 1 이면 "발급 수가 WARN_AT 에 닿았을 때 **그 DDL 의 커밋 안에서** 격자를 압축한다" |
| 소스의 상수·조건 | `sdnbModule.h:3718` — 회수 진입 조건은 `mMemberCnt >= SDNB_MEMBER_DIR_WARN_AT` |
| 산술 | 27 넣고 5 지웠으면 22. 4 파티션이면 멤버 4 |
| **차분** | 같은 일을 두 경로로 시키고 답을 맞댄다 — remap vs rebuild, 메모리 vs 디스크, 네이티브 vs `$GIT_`, 격리 수준 셋 |
| 원본 스위트 | `TC/Server/qp4/Project3/PROJ-1624-GlobalIndex` 의 `.lst` 가 그 시절의 정답이다 |

**차분 오라클이 가장 세다.** 절대값을 모르는 자리에서도 "둘이 같아야
한다" 는 말할 수 있고, 그 둘이 다르면 한쪽이 틀린 것이다.

### 4.3 픽스처는 코드에 닿을 만큼 크게

| 겨냥 | 필요한 규모 |
|---|---|
| 페이지 분할 · 노드 병합 · `COMPACT_INDEX_PAGE` · `FREE_KEYS` | 리프 여러 장 — 수천 행 + **대량 삭제** (삭제 없이는 `FREE_NODE_CNT` 가 0 이다) |
| 슬라이스 경계(병렬) | 워커 수 × 여러 페이지 |
| memberNo 격자 | 발급 수가 격자 경계를 넘어야 한다 |
| 키 길이 상한 | 경계 **바로 아래와 바로 위** 두 점 |

**행 수를 픽스처의 편의로 정하지 않는다.** 무엇을 밟아야 하는지에서
역산한다.

## 5. 어디를 겨눌 것인가 — 사냥 목록

현황판(§Coverage-Gaps 0.2)의 빈 축 다섯을 **"어디가 깨질 것 같은가"** 로
다시 적는다.

### H1. memberNo 발급 회계 — 반환되지 않는다는 계약

**설계**: 파티션 DDL 이 멤버 번호를 발급하고 **DROP 은 반환하지 않는다.**
그래서 회수가 따로 필요하다(GR-09). 하드 제약 6 이 경고한 자리다.

**예측**: (ADD PARTITION → DROP PARTITION) 를 k 번 돌리면
- 파티션 수는 제자리
- **`MEMBER_COUNT` 는 k 만큼 는다**
- `ACTIVE_MEMBER_COUNT` 는 제자리

**깨질 만한 이유**: 이 회계가 틀리면 회수 임계값에 언제 닿을지가 어긋난다.
그리고 이 축은 **커버리지 0** 이다.

### H2. 회수 임계값 — 사실상 도달 불가능한 코드

**실측**: `SDNB_MEMBER_DIR_GRID_8K = 400`, `PAGE_MAX = 20` →
상한 8,000, `WARN_PCT = 90` → **회수 진입은 발급 7,200 회**.

**그러므로 그 경로는 평범한 시험으로는 절대 안 돈다.** 한 번도 실행된 적
없을 가능성이 높고, 그런 코드가 결함을 품는다.

**할 일**: 7,200 회 DDL 은 비현실적이므로 **접근 가능한 대리 지표**를
찾는다 — 격자 페이지 경계(`MEMBER_DIR_GRID` 400) 를 넘기는 것은
가능한지, 뷰가 내는 `MEMBER_DIR_*` 값이 상수와 맞는지부터.

### H3. LEAVING 멤버의 purge 시점

**설계**: remap 은 나가는 멤버를 LEAVING 으로 두고 **커밋 시점 purge** 가
걷는다. `replacePartitionRemap` 이 remap 4 / rebuild 3 을 봤다 —
**purge 가 언제 그 하나를 걷는지는 아무도 안 쟀다.**

**예측 가능한 것**: 커밋 후 일정 시점에 `MEMBER_COUNT` == `ACTIVE_MEMBER_COUNT`
가 되어야 한다. 안 되면 누수다.

### H4. 페이지 압축과 키 회수 — 아직 한 번도 안 돌았다

§1.3 참조. 대량 삭제로 리프를 비워 `FREE_KEYS`·`COMPACT_INDEX_PAGE` 를
실제로 밟고, 그 뒤 **크래시 → redo** 를 건다. 지금 `restartRedoReplay` 가
못 하는 것이 정확히 이것이다.

### H5. 경계 두 점 — 상한 바로 아래와 위

`keySizeLimit` 은 사다리를 훑기만 하고 **경계를 집지 못했다**. 오류가
`3384`(글로벌) / `3386`(비글로벌) 을 직접 말해 주므로, 그 두 값을
**정확히 겨눈 두 점**으로 다시 쓴다. 인덱스 예산 64, 파티션 수 상한도 같다.

### H6. 차분 — 매체·구현·경로

같은 검증을 두 벌로 돌려 답을 맞댄다. 지금 스위트는 메모리 43 · 디스크 259
로 **비대칭**이고, 메모리 쪽에 대응이 없는 검증이 많다. 차분이 서면
절대값 없이도 판정이 된다.

---

## 6. 절차 — 케이스 하나를 만드는 순서

1. **자리를 고른다.** §3 의 H1~H6 중 하나, 또는 설계 문서가 "여기가
   delicate 하다" 고 적은 곳.
2. **정답을 유도한다.** 설계·소스·산술·차분 중 하나로. 유도가 안 되면
   그 자리는 아직 케이스로 만들 수 없다 — 먼저 읽는다.
3. **케이스를 쓴다.** §4.1 의 예측 블록을 **맨 위에 숫자로** 적는다.
   픽스처 규모는 §4.3 에서 역산한다.
4. **`.lst` 없이 돌린다.** FAIL 이 정상이다.
5. **`.out` 을 판정한다.**
   - 예측과 같다 → `.lst` 로 굳힌다. **두 번째 실행은 이웃과 함께** 돈다
     (단독 두 번은 전역 조회의 비결정성을 못 잡는다 — §Coverage-Gaps 9.10).
   - 다르다 → **설계로 설명되는가**를 묻는다.
     - 설명된다 → 예측이 틀렸다. 예측을 고치고 **왜 틀렸는지 케이스에 적는다.**
     - 설명 안 된다 → **결함 후보.** `.lst` 를 찍지 말고 보고한다.
6. **이빨을 확인한다.** 그 케이스가 잡겠다는 것을 일부러 깨뜨려 보고
   붉어지는지 본다(하드 제약 4). 안 붉어지면 케이스가 그 자리를 안 밟는
   것이다 — §1.3 이 그 실패의 예다.

## 7. 하지 않을 것

| 금지 | 이유 |
|---|---|
| 돌려 보고 나서 예측을 적기 | 그건 전사다 |
| 어긋남을 만나면 먼저 케이스를 고치기 | 반사적으로 제품 편을 든 것이 §1.2 다 |
| 픽스처 크기를 편의로 정하기 | §1.3 |
| 자기참조 불변식만 쓰기 | §1.1 |
| 판정 없이 `.out` 을 `.lst` 로 복사 | 이 방법이 아니다 |
| 결함 후보를 기대값으로 굳히기 | 스위트가 결함 편을 들게 된다 |

## 9. 이 문서가 스스로에게 거는 조건

이 방법이 옳은지는 **결함을 찾는가**로만 판정된다. 그러므로:

- 이 방법으로 케이스를 쓴 뒤에도 **결함 후보가 0 이면**, 방법이 아직
  틀렸거나 겨냥이 얕은 것이다. "제품이 옳아서" 라고 결론짓기 전에
  §6 절차 6(이빨 확인)을 반드시 돌린다.
- **결함 후보를 찾으면 `.lst` 를 찍지 않는다.** 보고가 먼저다.
- 이 문서의 §2 표는 **이력이 늘면 갱신한다.** 새로 찾은 결함의 모양이
  비대칭이 아니면 §3 의 여섯 수를 다시 짠다.
